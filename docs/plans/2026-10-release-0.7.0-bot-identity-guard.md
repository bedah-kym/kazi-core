# Plan: 0.7.0 release — refuse to adopt a person's `kazi` account as the bot
Status: approved by Bedan on 2026-10-04 ("Apply"); applied on `release/v0.7.0`.

## Goal
Upgrading to 0.7.0 can never bind the assistant's identity to an existing human account named `kazi`; the upgrade stops with a clear message instead.

## Non-goals
- Guarding the run-time `get_or_create(username='kazi')` call sites (`users/signals.py`, `chatbot/consumers.py`, `chatbot/tasks.py`). Once the upgrade guard has passed and the name is reserved at registration, they can only find the bot.
- Renaming the person's account automatically. The operator chooses the new name.

## Touches
- Paths: `Backend/users/migrations/0018_rename_mathia_to_kazi.py` (guard in the "both accounts exist" branch); `Backend/users/naming.py` (`account_has_owner`); `Backend/chatbot/management/commands/seed_kazi.py` (same guard before adopting the account); `Backend/users/test_bot_identity.py` (new); `CHANGELOG.md`.
- Protected paths? yes: `Backend/**/migrations/*`. The migration has merged to `main` but has not shipped in a release.
- Contracts, migrations, approvals, payments, secrets? One data migration gains a precondition; no schema change.

## Risk class of any new action
None. The change only refuses.

## Approach
Found by CodeRabbit on PR #241, and by the release reviewer before it. In 0.6.0 the bot was `mathia` and `kazi` was an ordinary username. On upgrade, `users.0018` treats any existing `kazi` account as the bot and moves the old bot's room memberships to it; `seed_kazi`, which the container entrypoint runs after `migrate`, then adds that account to a room with every active user. Room access is by membership, so the person could read those rooms. An upgrade note alone does not protect an operator who pulls the new image and restarts.

An account "has an owner" when it has a usable password, a login history, or staff or superuser rights. The bot's account has none of these (it is created with no password and never logs in).

1. Migration: in the branch where both `mathia` and `kazi` exist, raise if `kazi` has an owner. Nothing is written before the check.
2. `seed_kazi`: raise `CommandError` on the same condition before `get_or_create`. This covers installs where no `mathia` account exists.
3. With `set -e` in the entrypoint the container stops at that point, so the server never starts with the wrong identity. The operator renames the account (`SKIP_MIGRATIONS=1` gets a shell) and restarts.

## Verification (executable)
- `manage.py test users.test_bot_identity`: 8 tests. Without the migration patch, `test_refuses_to_merge_the_bot_into_a_persons_account` fails with "RuntimeError not raised"; with it, all pass.
- Old behaviour kept: merging into an owner-less `kazi` account and the plain rename are both tested and unchanged.
- Full hermetic suite with the patch applied; flake8 and bandit on the changed files.
- Failure paths covered: the guard itself is the failure path; the test asserts nothing was changed when it fires.
- Injection corpus cases added: none (no model input involved).

## Rollback
`git apply -R` the patch and revert the commit. Databases that already ran `users.0018` are unaffected either way.

## Open questions for the human
- Is "staff or superuser" right as a sign of ownership? It errs toward refusing: an operator who made the bot account staff would have to remove that flag once.
