# Kazi Core v0.4 — Milestone Roadmap

**Status:** draft. Concrete issue backlog for the v0.4 cycle.
**Companion:** [`v0.4-brief.md`](v0.4-brief.md) — the *why* this list serves.

This file is intentionally a flat backlog with priorities, owners, and
acceptance criteria. It maps 1:1 to GitHub issues — each `### M-x` heading
is one issue title.

---

## Legend

- **P0** — must ship in v0.4.
- **P1** — should ship; cut last if scope slips.
- **P2** — desired; defer to v0.5 if needed.
- **Size:** S (≤1 day), M (2-4 days), L (≥1 week).
- **Origin:** `plan` (from the user-supplied v2 plan), `audit` (found while
  validating the plan against the current repo).

## Milestone 2 — One extension path (Weeks 2-4)

### M2-1 · `[P0][M][plan+audit]` Collapse the duplicate connector loading

- **Problem (audited):** `MCPRouter.__init__` (lines 77-109 of
  `Backend/orchestration/mcp_router.py`) hardcodes an action→connector
  dict that is near-identical to
  `connector_registry._load_legacy_connectors` (lines 147-176 of
  `Backend/orchestration/connector_registry.py`). Two places to update,
  two places to drift.
- **Plan:**
  1. Make `MCPRouter` consume `discover_connectors()` for its mapping;
     keep a `connectors` property as a read-through shim for one cycle.
  2. Delete `_load_legacy_connectors` after `MCPRouter` no longer needs
     it; legacy connectors get imported via the same scan as everything
     else.
  3. Add a deprecation warning on direct `MCPRouter.connectors` writes.
- **Acceptance:** there is exactly one place where action→connector
  mappings are produced. `validate_router_mappings` still passes. No
  behavior change in the agent loop's tool dispatch.
- **Tests:** `test_workflow_ungating.py` style coverage proving every
  catalog action resolves through the registry path.

### M2-2 · `[P0][M][plan]` Define and publish stable contracts

Document and version the contracts the rest of the system relies on:

- **Connector execution contract** — `execute(parameters, context) ->
  {"status", "message", "data"}` (already informal; promote to versioned
  spec).
- **Tool schema contract** — what `get_action_catalog_entries()` returns,
  validated by a schema check at startup.
- **Approval contract** — what `tool_executor` passes through the
  confirmation gate; what a user response shape must look like.
- **Memory update contract** — what `memory_state` accepts as a write,
  what entities/preferences look like over the wire.
- **Telemetry event contract** — the JSONL event shape consumers can
  rely on.

Lives at `docs/contracts/` (one file per contract). Each contract has a
version number and a "breaking changes since" log.

- **Acceptance:** every contract has a Pydantic / JSON schema and is
  imported by at least one runtime check.

### M2-3 · `[P1][L][audit]` Rename `mcp_router.py` and split inline connectors

- **Problem (audited):** `mcp_router.py` is 857 lines, defines the
  `MCPRouter` class *and* six inline connectors (`CalendarConnector`,
  `SearchConnector`, `WeatherConnector`, `GiphyConnector`,
  `CurrencyConnector`, `ReminderConnector`). The "MCP" name collides
  with Anthropic's now-standard Model Context Protocol and misleads OSS
  readers.
- **Plan:**
  1. Move each inline connector into its own file under
     `Backend/orchestration/connectors/` (one file per connector, same
     pattern as the others).
  2. Rename `MCPRouter` → `ToolRouter`; rename file to
     `tool_router.py`. Keep `mcp_router.py` as a one-line re-export
     shim for one cycle.
  3. Update `AGENTS.md` line 46 ("read `mcp_router.py` first") to point
     at the new file.
- **Acceptance:** `mcp_router.py` is < 50 lines (shim only). Each
  inline connector now lives in `connectors/<name>_connector.py`.

### M2-4 · `[P1][M][audit]` Split `chatbot/consumers.py` into focused modules

- **Problem (audited):** 2,380-line module mixing WebSocket lifecycle,
  agent loop integration, presence, voice handling, and event
  streaming.
- **Plan:** extract `presence.py`, `voice.py`, `agent_loop_bridge.py`
  from `consumers.py`; keep `ChatConsumer` as a thin orchestrator.
- **Acceptance:** no extracted module > 600 lines; `consumers.py` is
  the lifecycle entry point only.

## Milestone 3 — Demo mode and developer DX (Weeks 4-6)

### M3-1 · `[P0][M][plan]` Ship a `KAZI_DEMO_MODE` runtime flag

- When `KAZI_DEMO_MODE=true`:
  - All built-in connectors that need credentials swap to recorded /
    mocked responses.
  - `LLM_PROVIDER=mock` returns scripted responses for the killer-demo
    prompt.
  - The example connector (`example_connector.py`) is enabled
    automatically (no `KAZI_ENABLE_EXAMPLE_CONNECTOR` needed).
  - Boot logs make the mode obvious so nobody confuses demo data with
    real data.
- **Acceptance:** `docker compose up` with `KAZI_DEMO_MODE=true` reaches
  a healthy `/health` plus a working chat round-trip with no real API
  keys set.

### M3-2 · `[P0][S][audit]` Promote `examples/` to a top-level directory

- Create `examples/` at repo root.
- `examples/connectors/echo/` — the canonical "copy this to start"
  connector. Currently lives at
  `Backend/orchestration/connectors/example_connector.py` behind an opt-in
  env flag; move it out and make it the default starting point.
- `examples/workflows/<name>/` — one canonical multi-step workflow that
  exercises the manager verifier.
- **Acceptance:** README links to `examples/` from the "Quick Start"
  block; the example connector boots without any env flag.

### M3-3 · `[P0][L][plan]` Build the killer-demo end-to-end script

- A `scripts/demo.sh` (or `make demo`) that:
  1. Boots the stack in demo mode.
  2. Sends the canonical follow-up-email prompt.
  3. Streams the planner decision, tool calls, confirmation gate,
     receipts, and memory mutation to stdout in a readable format.
- **Acceptance:** the demo runs in < 90 seconds on a clean clone with
  no API keys. Output is recordable as the public showcase.

### M3-4 · `[P1][M][plan]` Cut the local-run path to under 10 minutes

- Audit `docs/quickstart.md` against a stopwatch on a clean machine.
- Remove every step that is not strictly required to reach the demo.
- Move OAuth + production-only steps into `docs/deploy-safely.md`.
- **Acceptance:** the time-to-first-request SLA in the brief is met
  on at least two contributor machines.

## Milestone 4 — Observability as a headline (Weeks 6-8)

### M4-1 · `[P0][M][plan]` Promote the eval harness to a documented surface

- **Problem (audited):** `Backend/orchestration/eval/` already contains
  `golden_scenarios.json` and a `run_golden_eval` management command.
  Currently invisible in the README and docs.
- **Plan:**
  - Add `docs/eval.md` covering: how to add a scenario, how to run the
    harness, how to interpret pass/fail.
  - Wire the harness into CI as an advisory job (non-blocking) so
    regressions surface in PRs.
- **Acceptance:** `make eval` runs locally; a CI job reports
  pass/fail per scenario.

### M4-2 · `[P0][L][plan]` Render agent traces in a readable format

- Define a stable trace event schema (lives in `docs/contracts/`, see
  M2-2).
- Provide a `kazi trace <run_id>` CLI that prints the trace as a
  human-readable timeline (planner decision, tool calls,
  confirmations, retries, receipts, memory writes).
- **Acceptance:** the killer demo (M3-3) consumes this CLI for its
  output. A user can debug an agent run from the trace alone.

### M4-3 · `[P1][M][audit]` Consolidate `telemetry.py` and `tracing.py`

- **Problem (audited):** two adjacent observability surfaces. Decide
  on one (telemetry = events, tracing = spans) or unify.
- **Plan:** document the split or collapse it; export one `kazi.observe`
  surface that downstream code uses.
- **Acceptance:** `AGENTS.md` describes one observability story, not
  two.

### M4-4 · `[P2][M][plan]` Ship an OpenTelemetry exporter

- Optional OTLP exporter for trace events so users can plug into
  Honeycomb / Grafana / Tempo without writing a bridge.
- **Acceptance:** `KAZI_OTEL_ENDPOINT=...` produces spans in a
  standards-compliant collector.

## What is *not* on the roadmap (for the record)

To make the freeze tangible, here is what we are **not** doing in
v0.4 even though it has been raised:

- New connectors of any kind (Slack, Discord, Stripe, Notion, etc.).
- Multi-tenant admin UI.
- Pentest / bug-bounty feature (deferred per
  `docs/PENTEST_FEATURE_PLAN.md`).
- A hosted / Pro tier.
- Frontend in this repo (Mathia OS frontend stays in-house).
- Streaming `stream_message()` rehabilitation (the existing
  `create_message()` + simulated typing path is fine).

These are not rejected, only deferred. They surface again in the v0.5
brief if v0.4's foundation work succeeds.

---

## Cross-cutting acceptance for v0.4 itself

The release ships when **all P0 issues above** are merged *and* the four
success metrics from the brief are demonstrable on a clean machine:

- [ ] Local run in under 10 minutes.
- [ ] Add a connector in one file plus one test.
- [ ] 90-second demo runs end-to-end.
- [ ] At least one outside contribution lands in `examples/` or
      `connectors/`.

P1 items are not required to ship; they roll into v0.4.x patch releases
or v0.5 as the team prefers.
