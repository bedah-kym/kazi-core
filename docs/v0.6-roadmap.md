# Kazi Core v0.6 — Implementation Plan (Shell-first)

**Status:** draft for implementation
**Owner:** Bedan
**Linked brief:** [`v0.6-brief.md`](v0.6-brief.md)

This is the *how*. The brief is the *why*. Read the brief for the pillars and
the non-goals; this doc turns them into file-level work, with the shell as the
deepest section because that is the new direction.

---

## 1. Settled decisions (from design review)

| # | Decision |
|---|---|
| D1 | Three **isolation profiles**: `open` / `standard` / `locked`. |
| D2 | Default profile on fresh install: **`standard`**. |
| D3 | Two execution backends: **Docker** (`standard`/`locked`) and **direct subprocess** (`open`). |
| D4 | Network is **per-profile**: none (`locked`) / allowlist (`standard`) / full (`open`). |
| D5 | **Persistent workspace** across tasks; fresh read-only container per command. |
| D6 | Escalation is **two-tier**: inline confirm (bounded) + durable approval (destructive). |
| D7 | **`run_command` is THE shell**; `delegate` (opencode/Claude Code) is a later phase. |
| D8 | **Shell-host-only** reach in v0.6; remote-exec is deferred. |
| D9 | Loop budget **raised modestly** for shell sessions (still hard-bounded). |
| D10 | **Typed sysops connectors retired** (#129 closed) — the shell covers that reach. |

Core philosophy (from review): the **sandbox is the security boundary**; the
"classifier" is UX + a tripwire, not the boundary. Highways for power users,
safe roads for everyone else — both first-class, neither denied.

## 2. Architecture overview

```
Client → ChatConsumer → OrchestrationCoordinator → Agent Loop (ReAct)
                                                       │
                                                   Tool Executor
                                                       │  run_command (action)
                                                       ▼
                                              Dynamic risk gate (§4.3)
                                              safe / inline / durable / denied
                                                       │
                                         ShellConnector (thin; no policy)
                                                       │  HTTPS + shared secret
                                                       ▼
                                      shell-exec sidecar (on the shell host)
                                         ┌──────────────┴──────────────┐
                                         ▼                              ▼
                                Docker backend                   Local backend
                                (standard / locked)             (open)
                          docker run <profile flags>     subprocess in workspace
```

Two rules the whole design rests on:

1. **The sidecar is deliberately dumb.** It runs a command in a container (or
   subprocess) and returns stdout/stderr/exit. No classifier, no autopilot, no
   policy. All policy lives in Kazi's orchestration layer, next to the rest of
   the governance.
2. **Kazi never touches Docker or a raw shell itself.** Only the sidecar does.
   The sidecar holds no Kazi credentials and no Kazi secret — just a shared
   token and a workspace directory.

## 3. Isolation profiles

| | `open` (highway) | `standard` (default) | `locked` |
|---|---|---|---|
| Backend | direct subprocess | Docker | Docker |
| User | non-root (`kazi`); `allow_root` opt-in w/ loud banner | non-root (`--user` uid) | non-root |
| Root filesystem | full (subject to user perms) | read-only | read-only |
| Writable | full (user perms) | `/workspace` only | none (ephemeral `/tmp`) |
| Network | full | on/off per command (§4.5) | none |
| Escalation | destructive → inline; root → inline | network → inline; destructive → durable | any non-read → durable/deny |
| For | a disposable box | a normal machine | a machine with real stuff |

`open` is **not the default** and ships a boot warning equivalent to
`KAZI_DEMO_MODE`'s banner, because "full power, all access" on a box with real
stuff is the one thing that bites. It is available, not encouraged.

## 4. The shell — detailed design

### 4.1 Components

| Component | Where | What it does |
|---|---|---|
| `ShellConnector` | `orchestration/connectors/shell_connector.py` | Registers `run_command`; forwards to the sidecar. No policy. |
| Dynamic risk gate | `orchestration/shell/classifier.py` + a hook in `get_tool_risk_info` | Decides safe / inline / durable / denied per command (§4.3). |
| Profile resolution | `orchestration/shell/profiles.py` | Loads `open`/`standard`/`locked` + per-room override. |
| Sidecar | `orchestration/shell_exec/daemon.py` (new entrypoint `manage.py run_shell_exec`) | `POST /exec` → Docker or subprocess. |
| Backends | `orchestration/shell_exec/backends.py` | `DockerBackend`, `LocalBackend` behind one `execute()` interface. |
| Config | `Backend/Backend/settings.py` | `SHELL_EXEC_*` (host, token, profile, timeouts, image, caps). |

### 4.2 `run_command` action

```python
# params
command:    str    # required; the raw command
cwd:        str    # optional; default = /workspace
timeout_s:  int    # optional; default 120, capped by SHELL_EXEC_TIMEOUT_MAX
```

Registered with `risk_level: high`, but its *effective* risk is **dynamic** —
the static `confirmation_policy` is not used for this action (see §4.3).

### 4.3 The permission model (default-deny sandbox + escalation)

The command string is **not** parsed for safety. Instead, the sandbox defaults
to a state where the agent can do no harm, and the only decision that needs a
human is *escalation out of that state*.

For a given `(command, profile)`, the classifier returns one tier:

| Tier | Meaning | Behavior |
|---|---|---|
| `safe` | read-only, non-root, within the profile envelope | auto-execute |
| `bounded` | needs network (allowlisted host) or writes to workspace | inline confirm (§4.4) |
| `destructive` | tripwire match (`rm -rf`, `dd`, `mkfs`, …) | durable approval (§4.4) |
| `denied` | out of envelope for this profile (network in `locked`, root in `standard`) | refuse with a clear message |

The classifier is three small, honest checks — not a regex firewall:

1. **Needs root?** (`sudo`, `su`, setuid). → escalate/deny.
2. **Needs network?** a conservative list of network-touching binaries
   (`ping`, `dig`, `curl`, `wget`, `nslookup`, `ssh`, `nc`, `git clone`,
   `pip install`, `apt`, …). → escalate (or deny in `locked`).
3. **Destructive tripwire?** a short blocklist. → durable approval.

**Everything else is enforced by the sandbox, not the classifier.** A write
command that slips past the tripwire can still only write to `/workspace`
(read-only rootfs) as non-root with `--cap-drop=ALL`. A network command that
slips past the network list still runs with `--network=none`. That is the
entire point: a false negative in the classifier costs nothing, because the
sandbox already bounded it.

### 4.4 Two-tier escalation

- **Inline confirm** (`bounded`): a lightweight pause in the chat — "run
  `curl https://…`? [allow / deny]". Reuses the existing agent-loop
  confirmation pause, but short-lived and chat-scoped.
- **Durable approval** (`destructive`): a `WorkflowApprovalRecord`
  (`kind=agent_loop`), the existing durable path — survives Redis eviction,
  shows in the ops inbox, leaves a receipt.

This maps onto the loop's existing `safe_calls` / `confirm_calls` split with
one small change: the risk gate must become **dynamic** (see §4.7), and the
confirm path must distinguish inline vs durable by a `tier` field.

### 4.5 Network model (honest scoping)

The hard, enforceable boundary is **network on/off per command**:

- `locked`: always `--network=none`.
- `standard`: `--network=none` by default; a command flagged "needs network"
  runs with `--network=bridge` **only after** the inline-confirm (or, if the
  host is in the user's allowlist, without prompting).
- `open`: full network (no Docker).

The **host allowlist is a UX shortlist**, not a firewall: it decides which
hosts skip the inline prompt. True per-host egress filtering (a firewall
container / iptables) is a later hardening — listed in §10. This is the honest
trade: "ping my ISP" works today, and default-deny network is still real, but
"no route to credential stores" is *procedural* (the sidecar's network and the
allowlist), not enforced packet-by-packet, until the hardening lands.

### 4.6 State & workspace

- The sidecar owns a workspace dir per room: `<SHELL_EXEC_ROOT>/workspaces/<room_id>/`.
- Docker backend mounts it at `/workspace` (rw) with a non-root uid that owns
  it; rootfs is read-only. Local backend runs `cwd=<workspace>`.
- Persistence = the dir survives across commands, so installed tools and
  scripts accumulate (the "gets better over time" property).
- Snapshot/rollback: `tar` the workspace before any `destructive` approval;
  ZFS/btrfs snapshots are a later optimization.

### 4.7 Caps & budgets (the one existing-code change)

- **Dynamic risk gate**: `get_tool_risk_info(tool_name, preferences)` must gain
  `tool_input` and, for `run_command`, dispatch to the shell classifier. This
  is the "governance hook" the brief deferred — the shell makes it *necessary*,
  not optional. It is the only change to existing loop logic.
- **Loop budget**: raise the shell-session caps modestly (D9) — e.g. tool-call
  cap 15 → ~25 for sessions that touch the shell, with the hard backstop
  (`HARD_CAP_*`) untouched. Iteration/token caps stay.
- **Sidecar caps** (enforced independent of Kazi): `timeout_s_max`,
  `output_bytes_max`, Docker `--memory` + `--pids-limit`.
- **Output** flows through the existing `_sanitize_tool_result` (8k cap +
  result-injection regex) before it reaches the LLM.

### 4.9 Flagship scenarios traced

1. **"Ping my ISP"** (`standard`): `run_command{ping -c 4 <gateway>}` →
   classifier: needs network, host in allowlist → `bounded`, auto-allowed →
   sidecar Docker `--network=bridge` → output → reply. No prompt.
2. **"Why is this container restarting?"** — v0.6 is shell-host-only (D8), so
   this works **only if the sidecar runs on that host**. Diagnosing *other*
   machines is the deferred remote-exec backend (§10). Called out explicitly so
   nobody is surprised.
3. **"Sing a lullaby"** — Pillar 2 (TTS connector), no shell at all.

## 5. Learning foundation (L1–L3, ships after the shell)

The brief's §5: Jarvis earns initiative, it never grabs it. The v0.6 slice is
three beat-task-sized pieces; the full arc (procedural memory, self-improving
workflows) is v0.7 — epic #160.

- **L1 — Telemetry rollups** (#153): nightly beat task turns JSONL telemetry
  into entity facts (hosts, services, device names) and derived watches (disk
  growth, failure correlation). Deterministic arithmetic, no LLM.
- **L2 — Preference mining** (#152): approve/deny history → learned
  `approval_overrides` with confidence thresholds. Denials outrank approvals;
  reversible and room-scoped.
- **L3 — Initiative ladder** (#154): rung 2 daily digest → rung 3 propose
  (with diff) → rung 4 promote (one durable approval, then automatic with
  receipts). Hard caps: proactive budget per day; proactive actions never
  exceed the safe tier unless an approved rule exists.

None of these execute anything new — they compute, digest, and propose. Every
promotion routes through the existing durable approval seam.

## 6. Pillar 2 — generation connectors (modality)

`generate_speech` (TTS) as a typed connector + a per-channel capability flag
(`supports_voice`, `max_audio_bytes`) on the notifications module + one
prompt hint ("when asked to sing/speak, prefer a voice tool"). No new pipeline
stage. Ship after the shell, since it needs none of §4.

## 7. Pillar 3 — delegation (deferred, queued for v0.7+)

`delegate` = hand the whole task to opencode/Claude Code headless in a
sandboxed container. The **spike** (Phase 0) settles which runtime; the
**credential spec** (Phase 0) settles the scoping. **Not started** until the
shell is real and used. Procedural memory (brief §5) is v0.7+.

## 8. Phases

**Phase 0 — settle (parallel, no shell code).**
1. Docs rewrite: shell-first brief + this roadmap alignment (#151).
2. Spike: opencode vs Claude Code headless, 1-day timebox (queued for whenever
   Pillar-3 delegation reopens — v0.7+; #125).
3. Credential-scoping spec (filesystem / egress / keys / revocation).
4. Extend the prompt-injection corpus with shell-command cases.
5. Write the brief's §8 success metrics as failing tests first.

**Phase 1 — shell MVP (`standard` only, everything gated).** Sidecar + Docker
backend + `run_command` + dynamic risk gate, where *all* escalation is durable
approval (no inline yet). Acceptance: `run_command{echo hi}` round-trips
through the sidecar in a non-root, read-only, network-none container. Also the
acceptance for the retired typed-connector path: "ping my ISP" resolves
through `run_command` with the host allowlisted.

**Phase 2 — full shell.** `open`/`locked` profiles, two-tier escalation,
network on/off + allowlist UX, persistent workspace + tar snapshot. Acceptance:
the §4.3 tier table behaves as specified; destructive → durable approval.

**Phase 3 — Pillar 2 (modality).** `generate_speech` + delivery flag + hint.

**Phase 4 — learning foundation.** L1 telemetry rollups, L2 preference mining,
L3 initiative ladder (#153, #152, #154).

**Phase 5 (later).** v0.7: procedural memory, God-tier workflows (epic #160),
and the delegation question (§10 of the brief).

## 9. Test plan

- Classifier: every tier × profile combination, plus edge cases (obfuscated
  destructive command still → `safe` but sandbox-bounded; network command in
  `locked` → `denied`).
- Profile resolution + default = `standard`.
- Sidecar backends: Docker mocked; local backend against trivial commands
  (`echo`, `pwd`) in a temp workspace.
- Connector: happy path + error path (sidecar down → normalized error).
- Learning: L1 rollups over fixture telemetry; L2 thresholds/denial reset/room
  scoping; L3 ladder rungs, proactive budget cap, no-rule → no-auto-action.
- **Injection corpus**: shell + digest/proposal prompt-injection cases run in CI.
- **Budget**: a shell session respects the raised cap and the hard backstop.
- **Metrics-as-tests** (§8 of the brief), written before the shell work.

## 10. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Prompt injection via shell output | `_sanitize_tool_result` + result-injection regex + corpus |
| Container escape | `--cap-drop=ALL`, non-root, read-only rootfs, `--network=none`, mem/pid caps |
| Docker socket exposure | only the sidecar touches Docker; Kazi never does |
| Command/arg injection | command passed as argv (no shell interpolation of structured input); the raw-shell mode is explicitly gated |
| Cost blowup | loop caps + per-command timeout + output caps, all hard-bounded |
| `open` footgun | not default; loud banner; destructive tripwire still fires |

## 11. Deferred / open (honest)

- True per-host egress firewall (v0.6 = network on/off + allowlist-as-UX).
- Remote-exec (ssh) backend for diagnosing *other* machines.
- mTLS instead of the shared secret.
- ZFS/btrfs workspace snapshots (tar first).
- Windows/PowerShell profile (bash-first).
- Which runtime the spike picks for `delegate` (Phase 0, Q1).
