# Kazi Core v0.4 — Product Brief

**Status:** draft. Scope-setting artifact for the v0.4 release cycle.
**Owners:** maintainers.
**Linked roadmap:** [`v0.4-roadmap.md`](v0.4-roadmap.md).

---

## 1. The one-sentence story

> **Kazi Core is the self-hosted runtime for tool-using agents.**

Everything in v0.4 is judged against that sentence. If a feature, page,
connector, or doc does not pull weight on *self-hosted*, *runtime*, *tool-using*,
or *agents*, it is moved out of the headline path.

## 2. Why v0.4 (and why now)

v0.2.0 opened the orchestration core. v0.3.0 hardened the repo for outside
contributors (AGENTS.md, signed releases, real-Postgres CI, Python 3.11/3.12
matrix). The repo is *safe to onboard onto* but it is **not yet legible**:

- The README sells eight value propositions and a dozen connectors at once,
  so a reader cannot answer "what is this?" in 10 seconds.
- Two extension paths exist for connectors (hardcoded `MCPRouter.connectors`
  dict + `connector_registry.discover_connectors()`), so a contributor cannot
  answer "how do I add one?" in 5 minutes without reading both.
- Vertical features (travel, payments) are interleaved with the agent core,
  so a self-hoster cannot tell what they need versus what they can rip out.
- There is no "watch one tool call, inspect one trace" path, so an evaluator
  cannot feel the product without wiring real API keys.

v0.4 is the cycle that makes the project **legible, scoped, and demonstrable**
before we widen the surface area again.

## 3. Non-goals

These are explicitly *out* of scope for v0.4:

- **No new vertical connectors.** No new payment rails, travel providers,
  messaging channels, or domain modules. Connector sprawl resumes after the
  extension story is one path, not two.
- **No new domain features** (analytics dashboards, billing UI, scheduling
  surfaces, multi-tenant admin). These return after the runtime story is clean.
- **No attempt to recreate the private Mathia OS frontend.** The OSS repo
  intentionally does not ship a UI in v0.4. If a demo UI lands, it lives under
  `examples/` and is explicitly minimal.
- **No breaking API rewrites.** Where contracts change, we deprecate-with-shim
  for one minor cycle (e.g. legacy `MCPRouter.connectors` dict keeps working
  while we route reads through the registry).
- **No premature ML / RL / advanced planning research.** The agent loop is a
  ReAct loop. Improving it is not a v0.4 goal.

## 4. Core vs optional — what the runtime *is*

This is the line we draw for v0.4.

### Core (the runtime — always shipped, always documented)

| Module | Path | Why it is core |
|---|---|---|
| Agent loop | `Backend/orchestration/agent_loop.py` | The think→act→observe engine. The product. |
| Workflow planner | `Backend/orchestration/workflow_planner.py` | Multi-step decomposition. |
| Manager verifier | `Backend/orchestration/manager_verifier.py` | Deterministic plan check. Distinctive. |
| Tool executor | `Backend/orchestration/tool_executor.py` | Risk gates, confirmation, execution. |
| Connector SDK | `Backend/orchestration/base_connector.py`, `connector_registry.py` | The single extension surface. |
| Action catalog | `Backend/orchestration/action_catalog.py` | Tool definitions + risk levels. |
| Security policy | `Backend/orchestration/security_policy.py` | Injection detection, sanitization. |
| Action receipts | `Backend/orchestration/action_receipts.py` | Audit trail — observability primitive. |
| Memory state | `Backend/orchestration/memory_state.py` | Entity tracking + preferences. |
| LLM client | `Backend/orchestration/llm_client.py` | Provider abstraction. |
| Telemetry / tracing | `Backend/orchestration/telemetry.py`, `tracing.py` | Observability — promoted to headline in v0.4. |
| Eval harness | `Backend/orchestration/eval/` | Golden scenarios — promoted to headline in v0.4. |

### Showcase (kept, but reframed as examples — not core identity)

| Module | What it becomes in v0.4 |
|---|---|
| `Backend/travel/` + travel connectors | A *showcase module* demonstrating multi-vendor connector patterns. Not in the headline pitch. |
| `Backend/payments/` + invoice/intersend connectors | A *showcase module* demonstrating high-risk action gating + receipts. Not in the headline pitch. |
| Notifications | A *showcase module* demonstrating the unified-routing pattern. Stays useful, leaves the headline. |
| Built-in Gmail / WhatsApp / Calendly / Mailgun connectors | Stay shipped, demoted from "look at all this" to "reference implementations of `BaseConnector`". |

### Out of repo (Mathia OS — `.gitignore`d on purpose)

`frontend/` and parts of `docs/` belong to the in-house Mathia SaaS and are
not part of Kazi Core. v0.4 should make this boundary explicit in the README
so readers stop expecting a UI in this repo.

## 5. The five flows v0.4 must make obvious

Every developer-facing artifact (README, quickstart, docs index) is graded
against whether these flows are findable in under five minutes:

1. **Run locally** — boot the runtime against a local stack, send one
   request, see one response. Demo mode (mock connectors, fake creds) is on
   by default.
2. **Add one connector** — copy `examples/connectors/echo/`, change three
   strings, restart, see the agent call it. One file plus one test.
3. **Add one workflow** — copy `examples/workflows/<example>/`, edit the
   plan template, run it. Manager verifier reorders it and shows why.
4. **Debug an agent run** — open the trace for a request and see: planner
   decision → tool call → confirmation gate → result → memory mutation →
   receipt. Each step is a real artifact with a stable shape.
5. **Deploy safely** — what to set, what to lock down, what to monitor,
   what *not* to expose. One page, not a tour of `settings.py`.

## 6. The killer demo

One end-to-end flow, scriptable, recordable, < 90 seconds:

> A user asks the agent to "send Alex a follow-up about tomorrow's meeting."
> The planner produces a two-step plan: `lookup_contact` → `send_email`.
> The manager verifier validates the plan. The tool executor runs
> `lookup_contact` (low-risk, no gate), pauses on `send_email` for
> confirmation (high-risk), records both as receipts, updates memory with
> the resolved contact, and the trace shows every step.

Every primitive in the demo is already in the codebase. v0.4's job is to
make them **work in demo mode without real API keys** and to **render the
trace in a way an outsider can read**.

## 7. Success metrics

Lifted from the user plan, kept verbatim because they are good:

- A new dev gets a local run working in under **10 minutes**.
- A new connector can be added in **one file plus one test**.
- One demo explains the value in under **90 seconds**.
- More outside contributions land in **examples and connectors**, not just docs.

Tracking instrumentation:
- `time-to-first-request` measured from `git clone` to `200 OK` on the demo
  endpoint, recorded in `docs/quickstart.md` as a SLA we hold ourselves to.
- Connector contribution count tracked via the `connector` PR label.

## 8. What success does *not* look like

Stating it explicitly so we do not drift back into v0.3 habits:

- "We added six new connectors" — fail. Sprawl is the problem we are
  solving.
- "We rewrote the agent loop" — fail. The loop works. The packaging does
  not.
- "We shipped a Pro tier / a hosted version" — out of scope. v0.4 is OSS
  legibility.
- "We have 80% test coverage" — coverage is a side-effect of the eval
  harness work, not a target on its own.

## 9. Decision log

Decisions made in landing this brief:

- **`mcp_router.py` is being deprecated, not deleted, in v0.4.** The name
  collides with Anthropic's MCP (Model Context Protocol) and confuses OSS
  readers. The router responsibility moves to `connector_registry` +
  `tool_executor`, but the file stays as a legacy shim with a deprecation
  warning until v0.5.
- **`AGENTS.md` and the README will be updated in lockstep with code
  changes.** Documentation drift is what made v0.3 ship with `agents.md`
  ghost references; we do not repeat that.
- **The `examples/` directory becomes a first-class top-level path.** Not
  hidden under `Backend/`, not behind an env flag — visible and inviting.
