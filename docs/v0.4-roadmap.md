# Kazi Core v0.4 — Milestone Roadmap

**Status:** in flight. Concrete issue backlog for the v0.4 cycle.
**Companion:** [`v0.4-brief.md`](v0.4-brief.md) — the *why* this list serves.

This file is intentionally a flat backlog with priorities, owners, and
acceptance criteria. It maps 1:1 to GitHub issues — each `### M-x` heading
is one issue title.

## Milestone 2 — Runtime foundation (Week 2-4)

### M2-1 · `[P0][M][plan+audit]` Collapse the duplicate connector loading *(PR #36)*

- **Problem:** `MCPRouter.__init__` (lines 77-109) and
  `connector_registry._load_legacy_connectors` (lines 147-176) define
  near-identical action→connector dicts. Two places to drift, the
  contributor question "how do I add a connector?" needs two answers.
- **Done:** `MCPRouter.__init__` consumes `discover_connectors()` as
  the sole source. Net `-47/+6` in `mcp_router.py`. Regression test
  `test_router_consumes_registry_as_single_source` pins the
  unification.
- This is the precondition for the connector SDK being a clean
  extension surface that a human-in-the-loop runtime can rely on.

### M2-2 · `[P0][M][runtime+plan]` Stable runtime contracts

Document and version the contracts the rest of the system relies on,
with the workflow-runtime additions front-and-centre:

- **Connector execution contract** — `execute(parameters, context) ->
  {"status", "message", "data"}`.
- **Tool schema contract** — what `get_action_catalog_entries()` returns.
- **Approval contract** *(new in v0.4)* — `pending_approval` shape on
  `WorkflowExecution`; the request/response shape for approve/reject.
- **Execution-detail contract** *(new in v0.4)* — `WorkflowExecution`
  fields operators read: `status`, `current_step`, `waiting_reason`,
  `pending_approval`, `receipts`, `replay_hints`, `dead_letter_reason`.
- **Replay-safety contract** *(new in v0.4)* — how an action declares
  `replay_safe=True/False` in the catalog; how `replay_hints` are
  computed from the step list.
- **Memory update contract** — what `memory_state` accepts on writes.
- **Telemetry event contract** — JSONL event shape.

Lives at `docs/contracts/` (one file per contract, versioned).

- **Acceptance:** every contract has a Pydantic / JSON schema and is
  imported by at least one runtime check.

### M2-3 · `[P1][L][audit]` Rename `mcp_router.py` and split inline connectors

- **Problem:** `mcp_router.py` is 857 lines, defines `MCPRouter` *and*
  six inline connectors. The "MCP" name collides with Anthropic's
  Model Context Protocol.
- **Plan:**
  1. Move each inline connector into its own file under
     `Backend/orchestration/connectors/`.
  2. Rename `MCPRouter` → `ToolRouter`; rename file →
     `tool_router.py`. Keep `mcp_router.py` as a one-line re-export
     shim for one cycle.
  3. Update `AGENTS.md` line 46 and any other inline references.
- **Acceptance:** `mcp_router.py` is < 50 lines (shim only). Each
  inline connector now lives in `connectors/<name>_connector.py`.

### M2-4 · `[P2][M][audit]` Split `chatbot/consumers.py`

- **Problem:** 2,380-line module mixing WebSocket lifecycle, agent loop
  bridge, presence, voice, and event streaming.
- **Plan:** extract `presence.py`, `voice.py`,
  `agent_loop_bridge.py`; keep `ChatConsumer` as a thin orchestrator.
- Demoted to **P2** — it does not block the human-gated runtime
  headline. Land if cycle has slack.
- **Acceptance:** no extracted module > 600 lines.

## Milestone 3 — Human-gated runtime (Weeks 3-6) — **headline**

### M3-1 · `[P0][L][runtime]` Durable approval checkpoints

- Implement `pause_for_approval(step_id, payload)` in the workflow
  runtime. Pause persists to `WorkflowExecution.pending_approval` and
  to Temporal as a signal-wait.
- Notify operators via the configured channel (in-app, email,
  WhatsApp) using `notifications/`.
- Resume the run on `approve(step_id, decision, note)` /
  `reject(step_id, reason)`.
- The wait survives worker restart, deploy, and host crash.
- **Acceptance:** a workflow paused on `send_email` resumes correctly
  after a `docker compose restart workflow_worker`. Test in
  `Backend/workflows/tests.py`.

### M3-2 · `[P0][M][runtime]` Execution detail records

- Add (or extend) `WorkflowExecution` with: `status`, `current_step`,
  `waiting_reason`, `pending_approval`, `receipts`, `replay_hints`,
  `dead_letter_reason`.
- Migrations included.
- A single API call returns the operator-readable state of any run.
- **Acceptance:** `GET /api/workflows/<id>/` returns every field
  documented in M2-2's execution-detail contract.

### M3-3 · `[P0][M][runtime]` Operator controls (API + admin)

- HTTP endpoints: `approve`, `reject`, `cancel`, `rerun`, `pause`,
  `resume` (immediate and scheduled).
- Django admin actions for the same operations.
- All transitions emit a receipt for the audit trail.
- **Acceptance:** an operator can drive the canonical demo end-to-end
  using only the documented operator surface (no shell access, no DB
  writes).

### M3-4 · `[P0][M][runtime]` Deferred-run watchdog

- Celery beat job scans `WorkflowExecution` rows in `waiting_for_*`
  states.
- Exponential backoff on re-pings; max-wait dead-letter with the
  reason persisted on the execution row.
- **Acceptance:** a workflow waiting longer than its
  `max_wait_seconds` is dead-lettered with a clear reason; the
  operator UI/API surfaces it.

### M3-5 · `[P1][M][runtime]` Replay safety surfaced to operators

- Each catalog action declares `replay_safe=True/False`.
- The runtime computes `replay_hints` for an execution: per-step,
  whether re-running it is safe and which earlier steps that depend on.
- `rerun(execution_id, from_step)` refuses unsafe steps unless an
  explicit `force=True` is passed *and* logged in the receipt.
- **Acceptance:** rerunning the demo from `send_email` is allowed;
  rerunning from `lookup_contact` is blocked unless forced.

## Milestone 4 — Observability and demo (Week 5-7)

### M4-1 · `[P0][M][plan]` Promote the eval harness to a documented surface

- `Backend/orchestration/eval/` already contains `golden_scenarios.json`
  and a `run_golden_eval` management command. Currently invisible.

- **Acceptance:** `make eval` runs locally; CI reports per-scenario
  pass/fail.

### M4-2 · `[P0][L][plan+runtime]` Render agent and workflow traces

- Stable trace event schema (lives in `docs/contracts/`, see M2-2).
- `kazi trace <run_id>` CLI prints the trace as a human-readable
  timeline (planner → tool calls → approval pauses → operator
  decisions → receipts → memory writes → replay events).
- The demo workflow pack (M5-1) consumes this CLI for its output.
- **Acceptance:** a developer can debug an agent run end-to-end from
  the trace alone.

### M4-3 · `[P1][M][audit]` Consolidate `telemetry.py` and `tracing.py`

- Two adjacent observability surfaces. Decide on one (telemetry =
  events, tracing = spans) or unify; document the split or collapse.
- **Acceptance:** `AGENTS.md` describes one observability story.

### M4-4 · `[P2][M][plan]` OpenTelemetry exporter

- Optional OTLP exporter for trace events.
- **Acceptance:** `KAZI_OTEL_ENDPOINT=...` produces spans in a
  standards-compliant collector.

## Milestone 5 — Demo workflow pack and DX (Weeks 6-8)

### M5-1 · `[P0][L][runtime]` Demo workflow pack

The canonical end-to-end story under `examples/workflows/`:

> Request → workflow → approval → receipt → replay.

- `examples/workflows/follow_up_email/` (or similar) — a two-step
  workflow that exercises every v0.4 primitive.
- Boots in `KAZI_DEMO_MODE=true` with no real API keys.
- A `scripts/demo.sh` (or `make demo`) runs the full loop in under
  90 seconds.
- **Acceptance:** an outside evaluator can `git clone` and watch the
  demo work without touching `.env`.

### M5-2 · `[P0][M][plan]` Ship a `KAZI_DEMO_MODE` runtime flag

- Built-in connectors that need credentials swap to recorded / mocked
  responses.
- `LLM_PROVIDER=mock` returns scripted responses for the demo prompt.
- The example connector (`example_connector.py`) is enabled
  automatically.
- Boot logs make the mode obvious.
- **Acceptance:** `docker compose up` with `KAZI_DEMO_MODE=true`
  reaches a healthy `/health` plus the demo round-trip with no real
  API keys.

### M5-3 · `[P0][S][audit]` Promote `examples/` to a top-level directory

- Create `examples/` at repo root.
- `examples/connectors/echo/` — the canonical "copy this to start"
  connector. Currently lives at
  `Backend/orchestration/connectors/example_connector.py` behind an
  opt-in env flag; move it out, drop the flag.
- `examples/workflows/<name>/` — see M5-1.
- **Acceptance:** README links to `examples/` from the Quick Start
  block.

### M5-4 · `[P1][M][plan]` Cut the local-run path to under 10 minutes

- Audit `docs/quickstart.md` against a stopwatch on a clean machine.
- Move OAuth + production-only steps into `docs/deploy-safely.md`.
- **Acceptance:** time-to-first-approval SLA is met on at least two
  contributor machines.

### M5-5 · `[P1][M][plan]` Rewrite docs around the five flows

Replace the component layout with workflow-oriented pages:
1. `docs/run-locally.md`
2. `docs/add-a-connector.md` *(supersedes `writing-a-connector.md`)*
3. `docs/add-a-workflow.md` *(new)*
4. `docs/operate-a-workflow.md` *(new — owns the approval/replay UX)*
5. `docs/deploy-safely.md` *(new)*

- **Acceptance:** each flow has one authoritative page; README links
  in order.

### M5-6 · `[P1][S][audit]` Update `AGENTS.md` for v0.4 layout

- Repo map: new connector locations after M2-3; the workflow runtime
  surfaces.
- Add a section calling out demo mode as the default for AI agents
  exploring the repo.
- Reference `docs/v0.4-brief.md` and the freeze.

## What is *not* on the roadmap (for the record)

- New connectors of any kind.
- Multi-tenant admin UI.
- Pentest / bug-bounty feature (deferred per
  `docs/PENTEST_FEATURE_PLAN.md`).
- A hosted / Pro tier.
- Frontend in this repo (Mathia OS frontend stays in-house).
- A web UI for the operator inbox in v0.4 — operator surfaces ship
  as APIs + Django admin.
- Streaming `stream_message()` rehabilitation.

These are not rejected, only deferred. They surface again in the v0.5
brief if v0.4 succeeds.

## Cross-cutting acceptance for v0.4 itself

The release ships when **all P0 issues above** are merged *and* the
success metrics from the brief are demonstrable on a clean machine:

- [ ] Local run + demo workflow boots in under 10 minutes
- [ ] An operator can take the canonical demo through the
      `request → workflow → approval → receipt → replay` loop with no
      real API keys
- [ ] A new connector still lands in one file plus one test
- [ ] The 90-second demo runs end-to-end from `scripts/demo.sh`
- [ ] At least one outside contribution lands in
      `examples/workflows/` or `examples/connectors/`

P1 items are not required to ship; they roll into v0.4.x patch
releases or v0.5.
