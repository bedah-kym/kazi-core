## 0. The one-sentence story

> **Kazi becomes Jon's Jarvis the day Jon stops being the operator — when the
> house's needs reach Kazi through one governed pair of hands, and the only
> thing Jon ever touches is the "approve" button on the things that matter.**

### Jon, three months in

**Day one.** Jon installs Kazi on the old mini PC by the router. He's not a
sysadmin — he's a guy who works late, has a baby that won't sleep, and a
Pi-hole he set up from a YouTube video and now quietly fears. On setup Kazi
asks one real question: *"Which machines can I touch, and how much?"* Jon
clicks "be careful with the NAS, never ask me about pings and lookups, ask
before restarting anything, make me approve anything that deletes." He never
thinks about that screen again.

**Week one.** Jon's internet stutters mid-call. He types "is the internet
down?" Kazi pings the gateway, checks DNS, checks the ISP's edge — twenty
seconds, all in the safe tier, no prompts — and answers: *"Your connection's
fine. Pi-hole is answering slowly — it's been up 90 days and its cache is
thrashing. Want me to restart it?"* Jon says yes. Kazi restarts it, watches DNS
come back, and sends a receipt he'll never read. This is the moment: **Jon
stopped being the operator of his own house.**

**Month one.** Kazi has a workspace now, and it's been *collecting*. It
scripted the Friday-night backup check. It installed a little watchdog for the
smart plugs. It learned Jon's devices by name — "the printer," "dad's laptop,"
"the garage cam." Jon says things like "why won't the printer print" and Kazi
checks the queue, the service, the network path, and usually just fixes it.
**It got better every week without Jon ever writing a connector — because it
has hands, not a menu.**

**Month two — the crisis.** Jon's at a wedding, phone on silent. 3 a.m.: the
power blinks, the mini PC comes back, but the Pi-hole's config got mangled.
Kazi detects DNS is dead. It diagnoses autonomously — that's the safe tier. It
reaches the conclusion: *fix requires rewriting the config file and restarting
the service — destructive tier.* So it sends Jon's phone a single, durable
message: "DNS is down. Here's exactly what I'd change (diff included).
Approve?" Jon glances at the diff on the dance floor, taps yes. By the time he
gets home, the internet works and there's a receipt waiting: what was broken,
what it did, what it cost, how to undo it.

**Month three — the morning.** Jon's wife hands him the baby. "Make her stop
crying." He says — to no one in particular — "Kazi, sing her the song." And it
does: a soft voice note, in the room, no lyric-dump. Later that morning Kazi
says: *"NAS is at 92%. I cleared the old media cache — here's the space I
recovered. Also, the router logs show it hangs after storms; I'll watch it next
week."* **It's not a tool anymore. It's a member of the household who happens
to live in a box.**

What Jon never did: open a terminal. Write a connector. Worry about what it
was doing at 3 a.m. — because every action it ever took is in the trail,
replayable, with a human gate on anything that mattered.

| Jon's moment | What Kazi must have |
|---|---|
| "is the internet down?" — no prompts | Safe-tier autonomy: sandboxed `run_command` + host allowlist |
| One tap on a dance floor | Durable approval + diff + receipt — the governance seam |
| It scripts its own tools | Persistent workspace that accumulates capability |
| It knows "the printer" and "dad's laptop" | Entity memory + telemetry rollups (L1) |
| It sees the storm-hang coming | Derived watches + proactive checks (L1/L3) |
| She stops crying | Voice out via `generate_speech` + channel capability flags |
| He never opens a terminal | Shell reach as the default substrate — connectors die |
| He never worries at 3 a.m. | Receipts trail + isolation profiles |

## 1. Why v0.6 (and why now)

A beta tester asked the question that frames the whole cycle: *"opencode and
Claude Code just work on my computer — why can't this do that, but for regular
stuff instead of code?"* `ping my ISP`, for example.

The honest answer is architectural, not about intelligence. Coding agents "just
work" because they have a **general substrate + a permission model** — a shell,
a filesystem, a workspace, and an ask/allow/deny gate. Kazi only had typed
connectors, so a request with no matching connector dead-ends.

The first draft of this brief answered that with typed sysops connectors and
delegation to other runtimes. Design review rejected both as the *primary*:
connectors are a menu (every new ask is a new file, and the field is moving to
LLMs that use computers natively), and delegation is slow and borrowed. The
answer is simpler and bolder:

- **The substrate is a commodity.** Kazi runs a *governed* shell — the same
  substrate pattern coding agents use — and owns the one thing nobody else in
  self-hosted land has: the governance seam.
- **The sandbox is the security boundary.** The classifier is UX + a tripwire,
  never the boundary.
- **Governance is Kazi's actual moat.** Durable approval, receipts, replay,
  budget caps. The shell is new reach; the existing seam is what makes it
  Jarvis-safe.

---

## 2. The core insight

The instinct that produced the shell-exec design doc was right: *give the agent
room to act.* The mistake in the original brief was assuming Kazi should avoid
holding that room itself. It should hold it — **governed, sandboxed, and
revocable** — because that is the only way reach, modality, and governance meet
in one product.

Three ideas carry the whole cycle:

1. **Shell-first reach.** `run_command` through a deliberately-dumb sidecar
   into a sandboxed container. Safe tier runs silently; escalation pauses for a
   human; destructive tiers go through durable approval. One pair of hands,
   governed.
2. **Modality is a connector choice.** Voice/image are generation connectors
   plus a one-line prompt hint and channel capability flags — not a pipeline
   stage.
3. **Jarvis earns initiative.** Kazi never invents autonomy. It compounds what
   Jon repeatedly said yes to, one rung at a time (§5).

---

## 3. Non-goals

Hard lines, not preferences:

- **No *ungoverned* shell.** The agent never gets an unrestricted or root
  shell. The sandbox defaults to "can do no harm"; every escape from that state
  is a human decision.
- **No command classifier as a security boundary.** The classifier is a small,
  honest tripwire for UX (root? network? destructive?) — a false negative costs
  nothing because the sandbox already bounded the command.
- **No typed sysops connector family.** Dead scope (#129 closed) — the shell
  covers that reach, and connector-per-capability is a treadmill the field is
  leaving behind.
- **No new modality-selection pipeline stage.** Connector + hint + flags.
- **No procedural-memory curator this cycle.** That is v0.7+, once the shell
  has generated something real to promote.
- **No changes to the agent loop, tool executor, or connector registry
  contracts** — with one deliberate exception: `get_tool_risk_info` gains
  `tool_input` so `run_command` can route through the dynamic risk gate.

## 4. The two pillars (and one principle)

### 4.1 Pillar 1 — The governed shell (reach)

`run_command` as THE shell, dispatched through a deliberately-dumb sidecar into
a sandboxed container (Docker backend now, local backend later). The full
design — isolation profiles (`open`/`standard`/`locked`), two-tier escalation
(inline confirm + durable approval), per-command network on/off with a host
allowlist, persistent workspace with snapshot/rollback — lives in
`docs/v0.6-roadmap.md` §3–§4 and issues #130–#135.

Properties that make this safe *by construction*:

- **The sidecar is dumb.** It runs a command and returns stdout/stderr/exit
  code. No policy lives in it; all policy lives in Kazi's orchestration layer
  next to the rest of the governance. Kazi never touches Docker or a raw shell
  itself.
- **The sandbox bounds everything.** Non-root, read-only rootfs,
  `--cap-drop=ALL`, network off by default, memory/pid caps. A classifier false
  negative costs nothing.
- **The workspace persists.** Tools and scripts accumulate per room — the
  "gets better over time" property — with a tar snapshot before any destructive
  approval.

### 4.2 Pillar 2 — Generation connectors (modality)

`generate_speech` (TTS) as a first-class typed connector, per-channel
capability flags (`supports_voice`, `supports_image`, `max_audio_bytes`) on the
notifications module, and one prompt hint ("when the user asks you to sing,
speak, or play, prefer a voice tool"). Modality degrades gracefully — voice
unavailable → text with a note. (#136)

### 4.3 Governance — a principle, not a pillar

Kazi already ships ~90% of the governance layer: `risk_level` +
`requires_confirmation`, `preferences.approval_overrides`, durable
`WorkflowApprovalRecord` checkpoints, append-only receipts + replay safety,
agent/sub-agent budget caps. The shell consumes that seam through one change:
a **dynamic risk gate** (`get_tool_risk_info(tool_name, preferences,
tool_input)`) that dispatches `run_command` to the shell classifier and returns
a tier (`safe | bounded | destructive | denied`). That is the only change to
existing loop logic (#131).

### 4.4 Delegation — demoted

Delegating to opencode/Claude Code headless is now "later, and maybe never"
(#137, blocked). The shell covers the open-ended tail better than a borrowed
runtime: lower latency, same sandbox story, and the learning stays in Kazi's
world instead of the other runtime's.

## 5. Learning — Jarvis earns initiative (v0.6 foundation)

Kazi never wanders the house executing things freely. It earns initiative in
observable rungs, from four learning loops. The v0.6 slice is L1–L3; the full
procedural-memory and self-improving-workflows arc is v0.7 (#160).

**The four loops:**

1. **Telemetry rollups** (#153) — a nightly beat task crunches the JSONL
   telemetry into entity facts (hosts, services, "the printer" = this IP) and
   derived watches (disk growth, failure correlation, "Pi-hole restarts follow
   storms"). Pure arithmetic; no LLM.
2. **Preference mining** (#152) — approve/deny history is a labeled signal:
   N approvals / 0 denials → learned `auto` override; one denial → never
   auto-propose that action+entity again. Reversible, room-scoped, visible.
3. **Workspace accumulation** — the persistent shell workspace is Kazi's
   notebook; solved things become scripts and notes, and retrieval beats
   recomputation. (Free with Pillar 1.)
4. **Promotion proposals** (L3 rung 4, v0.7 full arc) — repeated patterns with
   100% approval become *drafted rules* that go through durable approval once
   before they run automatically, with a receipt every time.

**The initiative ladder** (#154):

| Rung | Behavior | Earned by |
|---|---|---|
| 1 | Watch silently, log it | existing (free) |
| 2 | Mention it in the daily digest | anomaly above threshold |
| 3 | Propose a specific action (with diff) | repeated similar asks + no denials |
| 4 | Auto-execute under an approved rule | Jon approved the rule once, durably |

Hard caps: a proactive budget per day, and proactive actions never exceed the
safe tier unless an approved rule exists. Nothing self-authorizes.

---

## 6. Isolation: the two hard lines

1. **Least privilege, always.** No root, no `sudo` without an explicit human
   approval that can never be auto-approved. The agent account writes only to
   its own workspace; it reads the rest of the system, it never owns it.
2. **The agent host is never the infra host.** It runs on its own machine or
   container and *reaches* the home-lab services over the network. If it is
   diagnosing a DNS failure, it is not the DNS server.

Plus one standing rule: the agent host's outbound network is allowlisted, and
there is no route to credential stores or production systems.

## 7. Phased rollout (and where to stop)

1. **Phase 0 — foundations:** docs (this brief, #151), credential spec (#126),
   injection corpus (#127), metrics-as-failing-tests (#128).
2. **Phase 1 — shell MVP:** sidecar + Docker backend + `run_command` + dynamic
   risk gate, `standard` profile only, *everything* gated (#130–#131).
   **Stop here until the shell is real and used.**
3. **Phase 2 — full shell:** profiles, two-tier escalation, network toggle +
   allowlist, persistent workspace + snapshot (#132–#135).
4. **Phase 3 — modality:** `generate_speech` + delivery flag + hint (#136).
5. **Phase 4 — learning foundation:** L1 telemetry rollups, L2 preference
   mining, L3 initiative ladder (#153, #152, #154).
6. **v0.7+ (not v0.6):** procedural-memory promotion, God-tier workflows
   (versioning, promotion pipeline, health watches, reviewer agent, standing
   approvals — epic #160), and the delegation question, including the #125
   runtime spike (open, §10). The spike only runs if delegation reopens.

## 8. Success metrics

- A user asks "ping my ISP" or "why is the DNS failing" and Kazi answers by
  running **sandboxed, allowlisted** commands — no prompt on the safe tier.
- A high-risk action (restart a service, destructive change) **pauses for a
  human** with a diff, and produces a receipt.
- "Sing the baby a lullaby" resolves to a **voice note on a voice-capable
  channel** without the user asking for voice.
- A task Jon repeats becomes a **proposed** workflow/rule — never silently
  automatic — and its promotions trace back to an approval Jon gave once.

## What success does *not* look like

- "Kazi has an elevated shell" — fail. That is the thing we are refusing.
- "We wrote a command classifier as the security boundary" — fail. The sandbox
  is the boundary.
- "We built a connector for every ask" — fail. The shell is the reach story.
- "We built a modality-selection layer" — fail. Connector + hint.
- "The agent loop got rewritten" — fail. It works; we're plugging into it.
- "It authorized itself" — fail. Everything self-initiated traces to a human
  grant, with receipts.

## 9. Decision log

- **Shell-first.** Borrow the substrate *pattern* (shell + sandbox + permission
  model), own the governance. Typed sysops connectors retired (#129).
- **Sandbox is the boundary, classifier is UX.** No regex firewall.
- **No elevated shell, no same-box.** Root and co-location with the infra it
  manages are the two bites we avoid so we don't rewrite the security model
  later, when Kazi is the brain.
- **Delegation demoted.** The shell covers the open-ended tail; the borrowed
  runtime is "later, maybe never" (#137 blocked).
- **Modality is a connector choice, not a layer.**
- **Jarvis earns initiative.** Learning loops propose; humans grant. The full
  self-improving-workflows arc (versioning, promotion, watches, reviewer,
  standing approvals) is v0.7 — epic #160.
- **Procedural memory is deferred** to v0.7+, once the shell has generated real
  repeated patterns to promote.

## 10. Open questions

1. **Delegate to *what*, if ever?** opencode is open-source and self-hosted but
   overlaps Kazi's niche; Claude Code is mature but Anthropic-bound. The #125
   spike stays queued for whenever Pillar-3 delegation reopens (v0.7+).
2. **Is Kazi the *caller* or the *provider*?** Delegating out vs. exposing
   Kazi's governed tools over MCP (other agents call in). The provider
   direction reuses the durable-approval seam where it's most defensible.
   Decide before any delegation work.
3. **Which shell profile defaults first?** `standard` (Docker, non-root,
   read-only, network-off) — settled. Remaining question is only the per-command
   allowlist UX for "ping my ISP" with zero prompts.
4. **Windows/PowerShell profile** — bash-first; Windows profile deferred.
