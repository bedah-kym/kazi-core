# Kazi Core v0.4 — Product Brief

**Status:** in flight. Theme and scope for the v0.4 release cycle.
**Owners:** maintainers.
**Linked roadmap:** [`v0.4-roadmap.md`](v0.4-roadmap.md).

---

## 1. The one-sentence story

> **Kazi Core is the self-hostable runtime for human-supervised agent
> workflows.**

Everything in v0.4 is judged against that sentence. If a feature, page,
connector, or doc does not pull weight on *self-hostable*, *runtime*,
*human-supervised*, *agent*, or *workflows*, it is moved out of the
headline path.

## 2. Why v0.4 (and why now)

v0.2.0 opened the orchestration core. v0.3.0 hardened the repo for
contributors. The agent loop, the workflow planner, the manager verifier,
and the connector registry all work — the thing that does *not* yet exist
at runtime quality is the **human-in-the-loop seam**:

- A workflow can plan five steps but cannot pause for a real human
  approval that survives a server restart.
- Operators have no first-class place to see what is waiting on them or
  to act on it (approve, reject, cancel, rerun, pause, resume).
- "Replay safety" is a Temporal property, not a guarantee the runtime
  exposes to operators — there is no signal saying "rerunning step 3 is
  safe; rerunning step 5 will double-charge the user."
- Deferred runs (waiting on an external webhook, a scheduled time, a
  human) have no watchdog — if Temporal misses one, it goes silent.
- There is no end-to-end demo of `request → workflow → approval →
  receipt → replay` that an evaluator can run in 90 seconds.

v0.4 ships those primitives. The byproduct is that the runtime becomes
**legible and trustworthy** to outside developers, which is the
condition for everything else (more connectors, more workflows, more
contributors) to land safely after v0.4.

## 3. Non-goals

These are explicitly *out* of scope for v0.4:

- **No new vertical connectors.** No new payment rails, travel
  providers, messaging channels. Connector sprawl resumes after the
  human-in-the-loop seam is stable.
- **No new domain features** (analytics, billing UI, scheduling
  surfaces, multi-tenant admin). They return after the runtime story is
  trustworthy.
- **No attempt to recreate the private Mathia OS frontend.** The OSS
  repo intentionally does not ship a UI in v0.4. Operator surfaces ship
  as JSON APIs + Django admin in this cycle; a community web UI may
  follow under `examples/`.
- **No breaking API rewrites.** Where contracts change, deprecate-with-shim
  for one minor cycle.
- **No premature ML / RL / advanced planning research.** The agent loop
  is a ReAct loop. Improving it is not a v0.4 goal.

## 4. The five v0.4 deliverables

### 4.1 Durable approval checkpoints

A workflow step marked as requiring human approval pauses the run in
Temporal, persists a `pending_approval` record on `WorkflowExecution`,
notifies an operator over the configured channel(s), and resumes only
after an explicit approve/reject decision lands. The wait survives
worker restarts, deploys, and host crashes.

### 4.2 Execution detail records

`WorkflowExecution` carries the operator-visible state of a run:
`status`, `current_step`, `waiting_reason`, `pending_approval`, the list
of `receipts` produced so far, and `replay_hints` describing which steps
are safe to re-run. Anyone reading this row knows what is happening
without grepping logs.

### 4.3 Operator controls

A documented surface (HTTP API + Django admin actions) for:
- `approve(step_id, decision, note)`
- `reject(step_id, reason)`
- `cancel(execution_id, reason)`
- `rerun(execution_id, from_step)` — gated by replay-safety hints
- `pause(execution_id)` and `resume(execution_id)` — both immediate and
  scheduled

### 4.4 Deferred-run watchdog

For runs sitting in `waiting_for_*` states (approval, webhook,
scheduled time): a Celery beat job checks for staleness, applies
exponential backoff before re-pinging, and dead-letters runs that
exceed their max-wait policy. Operators see the dead-letter reason in
the execution detail.

### 4.5 Demo workflow pack

One canonical end-to-end story, scriptable and recordable, runnable in
under 90 seconds without real API keys:

> A user asks the agent to "send Alex a follow-up about tomorrow's
> meeting." The planner produces a two-step workflow: `lookup_contact`
> → `send_email`. The executor runs the lookup automatically, pauses
> on `send_email` for human approval, an operator approves it via the
> ops surface, the email goes out, the receipt and the resumption are
> visible in the execution detail, and the run is replayed from
> `send_email` to demonstrate replay safety.

Every primitive in this demo is implemented in v0.4. The pack lives
under `examples/workflows/` and is the canonical starting point.

## 5. Core vs optional — what the runtime *is*

This is the line we draw for v0.4.

### Core (the runtime — always shipped, always documented)

| Module | Path | Why it is core |
|---|---|---|
| Agent loop | `Backend/orchestration/agent_loop.py` | The think→act→observe engine. |
| Workflow planner | `Backend/orchestration/workflow_planner.py` | Multi-step decomposition; produces approval-gated plans. |
| Manager verifier | `Backend/orchestration/manager_verifier.py` | Deterministic plan check. |
| Tool executor | `Backend/orchestration/tool_executor.py` | Risk gates, confirmation. |
| **Workflow runtime** | `Backend/workflows/runtime.py`, `temporal_integration.py`, `models.py` | **The v0.4 headline.** Durable approvals, execution detail, operator controls, watchdog. |
| Connector SDK | `Backend/orchestration/base_connector.py`, `connector_registry.py` | Single extension surface (collapsed in M2-1). |
| Action catalog | `Backend/orchestration/action_catalog.py` | Tool definitions + risk levels. |
| Security policy | `Backend/orchestration/security_policy.py` | Injection detection, sanitization. |
| Action receipts | `Backend/orchestration/action_receipts.py` | Audit trail; consumed by execution detail. |
| Memory state | `Backend/orchestration/memory_state.py` | Entity tracking + preferences. |
| LLM client | `Backend/orchestration/llm_client.py` | Provider abstraction. |
| Notifications | `Backend/notifications/` | The seam workflow approvals reach operators through. |
| Telemetry / tracing | `Backend/orchestration/telemetry.py`, `tracing.py` | Observability — feeds the operator inbox. |

### Showcase (kept, but reframed as examples — not core identity)

| Module | What it becomes in v0.4 |
|---|---|
| `Backend/travel/` + travel connectors | A *showcase module* demonstrating multi-vendor connector patterns. Not in the headline pitch. |
| `Backend/payments/` + invoice/intersend connectors | A *showcase module* for high-risk action gating + receipts (a natural pairing with the human-in-the-loop seam). Not in the headline pitch. |
| Built-in Gmail / WhatsApp / Calendly / Mailgun connectors | Stay shipped; reframed as reference implementations of `BaseConnector`. |

### Out of repo (Mathia OS — `.gitignore`d on purpose)

`frontend/` and parts of `docs/` belong to the in-house Mathia SaaS and
are not part of Kazi Core.

## 6. Success metrics

- A new dev gets a local run working in under **10 minutes** with the
  demo workflow pack.
- An operator can take the full **approve → execute → receipt → replay**
  loop on the canonical demo with zero real API keys configured.
- A new connector can still be added in **one file plus one test** (the
  M2-1 collapse keeps this honest).
- One demo explains the value in under **90 seconds**.
- Outside contributions land in `examples/workflows/` and
  `examples/connectors/`, not just docs.

Tracking instrumentation:
- `time-to-first-approval` measured from `git clone` to a successful
  approve action on the demo, recorded in `docs/quickstart.md` as a SLA.
- Workflow runtime test coverage tracked separately from connector
  coverage so regressions in the v0.4 headline surface clearly.

## 7. What success does *not* look like

- "We added six new connectors" — fail. Connector sprawl is the problem
  we are deferring, not solving.
- "We rewrote the agent loop" — fail. The loop works.
- "We shipped a Pro tier / a hosted version" — out of scope.
- "We have 80% test coverage" — coverage is a side-effect of the
  workflow-runtime work and the demo pack, not a target on its own.
- "Replay works in Temporal" — necessary but not sufficient. Replay must
  be **legible to an operator** (replay_hints, safe-from-step markers),
  not just possible.

## 8. Decision log

Decisions made in landing this brief:

- **`mcp_router.py` was deprecated, not deleted, in v0.4.** The
  name collides with Anthropic's MCP (Model Context Protocol) and
  confuses OSS readers. The connector-resolution responsibility moves
  to `connector_registry` (M2-1, PR #36). The file was renamed to
  `tool_router.py` in v0.5, with `mcp_router.py` kept as a one-cycle
  re-export shim; the inline-connector split (M2-3) remains queued.
- **Operator surfaces ship as APIs + Django admin in v0.4, not as a web
  UI.** A community web UI may follow under `examples/`. Holding the
  UI back keeps the cycle focused on contracts.
- **Approval gates are part of the action catalog, not a separate
  concept.** A `requires_approval=True` flag on an action entry is what
  the runtime keys off; no parallel approval registry.
- **Replay safety is a per-step property surfaced as `replay_hints` on
  the execution detail.** Whether a step is safe to re-run is a
  property of the connector action, declared in the catalog, surfaced
  on the execution row, and enforced by the rerun control.
- **The connector + domain-feature freeze stays in effect for the
  cycle.** The docs PR (#35) makes this explicit; future contributors
  see the freeze before they propose a new connector.
